# Contributing to `@localess/nuxt`

Nuxt module wrapping `@localess/vue`. Read `CLAUDE.md` and
`docs/decisions/011-nuxt-module-depends-on-vue.md` first — this package is the one sanctioned
exception to rule 4, and the exception is narrow.

## Layout

```
src/
  module.ts                  defineNuxtModule — all build-time wiring
  types.ts                   ModuleOptions and the two runtimeConfig shapes
  runtime/
    plugin.ts                registers @localess/vue's Localess plugin (client + SSR)
    server/
      client.ts              useLocalessServerClient — the ONE localessClient(...) call
      index.ts               barrel behind the #localess/server alias
```

`src/module.ts` runs at build time in Node. `src/runtime/**` is shipped as-is and runs in the app.
Never import from `runtime/` inside `module.ts` except via `resolver.resolve()` — the module and the
runtime are different graphs.

## Sanctioned files (rule 7)

This package reaches `@localess/client` **only** through `@localess/vue`, which re-exports the
surface it needs. The designated files are:

| Role | File | May import |
|---|---|---|
| client | `src/runtime/server/client.ts` | `localessClient`, `LocalessClient` from `@localess/vue` — the only `localessClient(...)` call in the package |
| models | `src/types.ts` | client option types, if ever needed, via `@localess/vue` |

No file may import `@localess/client` directly. `src/module.ts` imports `localessComponentKeys` from
`@localess/vue/vite`, which is build-time-only and not a client import.

## Adding a module option

1. Add it to `ModuleOptions` in `src/types.ts` with JSDoc.
2. Decide **which runtime it belongs to** and add it to `PublicModuleOptions` or
   `PrivateModuleOptions` — never both. Anything secret goes private. If you are unsure, it is
   private.
3. Assign it in `setup()` in `src/module.ts`.
4. Consume it in `runtime/plugin.ts` (public) or `runtime/server/client.ts` (private).
5. Add a case to `src/module.setup.test.ts`. If the option is secret, assert it is absent from
   `runtimeConfig.public` — that suite is what stops a secret reaching the browser.
6. Update `SKILL.md`'s options table and `docs/nuxt.md`.

**Nuxt coerces `undefined` in `runtimeConfig` to `''`** so the value stays env-overridable. Any
option that is meaningfully absent must be normalised where it is read — see the `cacheTTL` handling
in `runtime/server/client.ts` and its test.

## Component registration

Keys come from `localessComponentKeys()` in `@localess/vue/vite`, so the convention is shared with
the Vue and React Vite plugins. Do not re-derive keys here.

The registry is generated by `addTemplate` with static imports rather than by delegating to
`@localess/vue/vite`'s `import.meta.glob` plugin. That is deliberate: the glob pattern is resolved
relative to the Vite root, which differs between Nuxt's client and Nitro builds and cannot express a
Windows absolute path. `generateComponentsTemplate()` is exported and unit-tested for this reason.

## Testing

```bash
npm test --workspace=@localess/nuxt
npm run build --workspace=@localess/nuxt
```

`@localess/vue` must be built first (`npm run build:vue`) — `module.ts` imports from its `dist`.

The end-to-end check is `playgrounds/nuxt`, which uses the module with no hand-written plugin. To
verify the token split against a real build:

```bash
cd playgrounds/nuxt
LOCALESS_PUBLIC_TOKEN=PUBLIC_SENTINEL LOCALESS_TOKEN=<real-token> npm run build
grep -r "<real-token>" .output/public     # must find nothing
grep -r "PUBLIC_SENTINEL" .output/public .output/server   # public token is expected
```

Use a *different* value for each token, or the grep cannot distinguish them.
